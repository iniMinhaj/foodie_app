# Migration Status

Tracks progress migrating `foodie_app` from setState to Clean Architecture + Riverpod (manual) + go_router, module by module. See [BUILD_SPEC.md](BUILD_SPEC.md) for the full spec and [../CLAUDE.md](../CLAUDE.md) for working conventions.

## Directory layout

- `lib/features/<module>/{data,domain,presentation}/` — every module is now migrated to Clean Architecture (`auth`, `home`, `restaurant`, `cart`, `profile`, `checkout`, `orders`, plus `search`, which is presentation-only — see below). Shared domain entities used across multiple modules live in `lib/core/entities/`, not inside any one feature. `CatalogRepository` (categories + paginated restaurant list) is `home`'s own repository; Search extends it directly with a `search(query)` method returning `SearchResults` (dedicated `SearchRestaurantResult`/`SearchProductResult` types, not padded `Restaurant`/`Product` entities, since the mock search response can't fully populate either) rather than duplicating a separate repository — `lib/features/search/` has no `data`/`domain` layer of its own. Restaurant Detail owns its own `RestaurantRepository` (single-restaurant + menu lookups) instead, since that's a distinct read shape from the paginated list and doesn't belong on `home`'s contract; Search also reuses `RestaurantRepository.getRestaurantById` to refetch a full `Restaurant` before navigating to Restaurant Detail from a tapped search result. Cart owns its own `CartRepository`, backed by `cart_sample.json`, and exposes `cartNotifierProvider` (an `AsyncNotifier`) as the single source of cart state for every screen that adds to or reads the cart. Profile reuses Auth's `UserProfile` entity directly (same "reuse, don't duplicate" reasoning as `CatalogRepository`/Search) and its own `ProfileLocalDataSource` reuses Auth's `UserModel` to read/write `users.json`, but only ever rewrites `full_name`/`phone`/`avatar_url`/`addresses`/`default_address_id` — password hash, loyalty points, payment methods and preferences round-trip untouched. `profileNotifierProvider` follows the same optimistic-update/persist/rollback shape as `cartNotifierProvider`. Checkout owns its own `CheckoutRepository` (write-only, appends to `orders.json`) and `checkoutNotifierProvider`, which tracks only the selected address/payment-method ids — the lists themselves are read straight off `profileNotifierProvider` rather than duplicated, and the restaurant name for the placed `Order` is resolved via `restaurant`'s `RestaurantRepository.getRestaurantById`. Orders owns its own read-only `OrdersRepository`/`OrdersLocalDataSource`, reading the same seeded `orders.json` Checkout writes to (fixing a previously-invisible bug where Checkout-placed orders never showed up in Order History), exposed as a plain `ordersProvider` (`FutureProvider`, no mutations, not `.autoDispose` since it's a persistent bottom-nav tab). The shared `Order` entity (`lib/core/entities/order.dart`) carries `orderNumber`/`restaurantLogoUrl`/`statusTimeline` — written once by Checkout, read by Orders — and `OrderStatus` has the full `{placed, confirmed, preparing, outForDelivery, delivered, cancelled}` set Orders' tracking timeline needs.
